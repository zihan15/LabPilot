# LabPilot portal — implementation map

This checkout is the **portal**, separate from the older `../app.py` workbench. The [offline diagram](docs/architecture.html) depicts the currently wired boundaries; [USER-GUIDE.md](USER-GUIDE.md) explains the UI and [DEPLOYMENT.md](DEPLOYMENT.md) covers host/handoff constraints.

## Repository map

| Path | Responsibility |
| --- | --- |
| `server.py` | Python standard-library threaded HTTP server, SQLite store, password sessions/CSRF, API routes, AWS CLI observation and exact-pin EC2 actions, role-selected Hermes CLI adapter, screenshot/vault handling. |

## Running topology and flows

`Browser over authenticated SSH tunnel → 127.0.0.1:8090 → server.py → SQLite / AWS CLI / Hermes CLI`. The portal binds loopback and checks localhost Host headers. It serves only the allowlisted static UI paths and `/api/*`; the HTML diagram is opened as a local file. Password login uses PBKDF2-HMAC-SHA256, server-side 12-hour sessions, an HttpOnly/SameSite=Strict cookie and an `X-CSRF-Token` on POSTs. Account changes revoke sessions and protect the last active admin. There is no HTTPS termination, SSO or MFA in the app; the tunnel is the private access path, **not permission to publish the service**.

**Inventory:** `GET /api/labs` synchronously uses AWS CLI `ec2 describe-instances` and `cloudformation list-stacks` in `ap-southeast-1`, mapping only known EC2 Name tags and two known MXHA stack names to labels. It returns observation time, source, EC2 state, stack status and errors, without instance IDs or private IPs. `productHealth` remains `unknown`. An EC2 running state is not a DAM/OS check; a failed observation is not silently treated as healthy.

**Existing EC2 actions:** `POST /api/labs/<lab>/start|stop` and `/api/labs/<lab>/components/<slot>/start|stop` accept no IDs or options. Start is available to tester/admin; stop to admin only. Two fixed three-component labs are backed by an out-of-repo 0600 pin file. The server validates **all** pinned IDs against exact Name tags before targeting stopped/running members, checks EC2 acknowledgement, reads state back, and records an attributed action. A process-local lock prevents simultaneous actions on one lab in this server; it is **not** a multi-worker or IAM lock. Timed-out/interrupted writes can have occurred: status becomes unknown/pending until inventory is refreshed. No termination, automatic stop, product check or tester SQL/instance command broker exists.

**Conversations:** `POST /api/sessions` creates an account-owned session tied to one known lab. New admin sessions use host Hermes `-t all` with the installed Imperva troubleshooting skill (up to 40 turns/420 seconds) and resume the linked private Hermes session; pre-upgrade sessions remain advisory. Tester sessions use safe mode with `todo` only (two turns/70 seconds), recent bounded chat history and no automatic live lab data. `POST /api/sessions/<id>/messages` persists a run, limited atomically to one active run per user. `GET /api/runs` drives two-second UI progress polling; stored steps are sanitized summaries, not raw tool output. Admins see cross-user activity metadata, **not** another user's prompts, replies, chat titles or run steps. Run origin is the portal, not a DAM appliance Gateway; other Hermes channels are not ingested.

A full-admin run can place a browser-captured PNG in a private per-run artifact directory next to SQLite. `GET /api/runs/<id>/screenshot` validates full-mode ownership, file type/size/pixels and serves no-store. The admin-only **Grant website login** form saves an identifier/password under one exact HTTPS origin in the **host-wide Hermes vault**; portal chat does not store that form password. Full-host admins share the vault. It is not a 2FA or shell/cloud approval mechanism. Login/role revocation is rechecked during full runs and kills the CLI process group; already-issued cloud calls or detached children are not rolled back.

**Requests and activity:** `POST /api/requests` records a lab-access note; it does not grant access. `POST /api/environments/requests` validates standalone MX/MXHA, 0–4 gateways, existing/new attachment, required MX version and purpose. It writes a pending ticket and proposes `LabPilot-{authenticated-user}-{topology}-{version}` (slugged), not a reserved resource. Admin decisions are recorded at `/api/requests/<id>/decision`; the requester cannot approve their own ticket. For approved typed environment tickets, `/api/requests/<id>/fulfillment` creates or reopens a private **full-host admin session** and returns an **unsent** review draft; requester purpose appears for admin review but is omitted from the agent draft. Admin must check name uniqueness, entitlement, costs, lifecycle and rollback separately. Approval is a **human handoff**, not enforced authorization: full admins can bypass the ticket through another session. There is no new-environment executor, database deployment flow, expiry/price enforcement or automatic teardown. Legacy note-only/versionless MX tickets require resubmission; legacy database requests cannot be fulfilled here. `/api/activity` mixes portal runs, requests and EC2 actions; its cross-user rows omit chat text and notes.

## Persistence and security boundary

SQLite defaults to `~/.local/share/labpilot/portal.sqlite` (0600); run screenshot artifacts live in `portal-artifacts/` beside it. The six exact EC2 pins are read from `~/.config/labpilot-portal/instance-allowlist.private.json` (owner-only 0600); initial bootstrap credentials, when present, are also private and **not** distributed in Git. Git ignores databases, `.env`, keys, credentials and private files. A fresh checkout alone does not reproduce this host's identities or pinned resources.

**Admin = trusted host/cloud operator.** Full Hermes inherits the host profile, private files and broad AWS `AdministratorAccess`. Tester safe mode limits exposed tools, but the worker also inherits the host OS identity; disabling IMDS for that process is not isolation. Exact-ID application checks do not substitute for narrow IAM or separate OS identities. Do not expose this password-only pilot to general teammates or a public endpoint. Independent worker/broker isolation, network/IMDS restrictions, HTTPS/SSO/MFA, audit retention and spend/expiry/cleanup enforcement are prerequisites for a wider deployment. See [DEPLOYMENT.md](DEPLOYMENT.md).
