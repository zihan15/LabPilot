# LabPilot portal — implementation map

This checkout is a **vibe-coded, AI-assisted proof of concept** for demonstrating Hermes harness-agent capabilities through a DAM-lab operating surface, separate from the older `../app.py` workbench. It is not a production agent security boundary or a complete automated reproduction pipeline. The [offline diagram](docs/architecture.html) depicts the currently wired boundaries; [USER-GUIDE.md](USER-GUIDE.md) explains the UI and [DEPLOYMENT.md](DEPLOYMENT.md) covers host/handoff constraints.

## Repository map

| Path | Responsibility |
| --- | --- |
| `server.py` | Python standard-library threaded HTTP server, SQLite store, password sessions/CSRF, API routes, AWS CLI observation and exact-pin EC2 actions, role-selected Hermes CLI adapter, screenshot/vault handling, skill-proposal review/promotion. |
| `static/index.html`, `static/app.js`, `static/operate.css` | Single-page UI, API calls, status rendering, two-second run polling, session-epoch cleanup of late responses, responsive styles. Font and OFL license are bundled in `static/`. |
| `test_portal.py`, `test_features.py`, `test_ui.mjs` | HTTP/backend/security and UI regressions; cloud/agent effects are mocked. |
| `docs/architecture.html` | Standalone inline-SVG architecture diagram; **not served as a portal route**. |

## Running topology and flows

`Browser over authenticated SSH tunnel → 127.0.0.1:8090 → server.py → SQLite / AWS CLI / Hermes CLI`. The portal binds loopback and checks localhost Host headers. It serves only the allowlisted static UI paths and `/api/*`; the HTML diagram is opened as a local file. Password login uses PBKDF2-HMAC-SHA256, server-side 12-hour sessions, an HttpOnly/SameSite=Strict cookie and an `X-CSRF-Token` on POSTs. Account changes revoke sessions and protect the last active admin. There is no HTTPS termination, SSO or MFA in the app; the tunnel is the private access path, **not permission to publish the service**.

**Inventory:** `GET /api/labs` synchronously uses AWS CLI `ec2 describe-instances` and `cloudformation list-stacks` in `ap-southeast-1`, mapping only known EC2 Name tags and two known MXHA stack names to labels. It returns observation time, source, EC2 state, stack status and errors, without instance IDs or private IPs. `productHealth` remains `unknown`. An EC2 running state is not a DAM/OS check; a failed observation is not silently treated as healthy.

**Existing EC2 actions:** `POST /api/labs/<lab>/start|stop` and `/api/labs/<lab>/components/<slot>/start|stop` accept no IDs or options. Start is available to tester/admin; stop to admin only. Two fixed three-component labs are backed by an out-of-repo 0600 pin file. The server validates **all** pinned IDs against exact Name tags before targeting stopped/running members, checks EC2 acknowledgement, reads state back, and records an attributed action. A process-local lock prevents simultaneous actions on one lab in this server; it is **not** a multi-worker or IAM lock. Timed-out/interrupted writes can have occurred: status becomes unknown/pending until inventory is refreshed. No termination, automatic stop, product check or tester SQL/instance command broker exists.

**Conversations:** `POST /api/sessions` creates an account-owned session tied to one known lab. New admin sessions use host Hermes `-t all` with the installed Imperva troubleshooting skill (up to 40 turns/420 seconds) and resume the linked private Hermes session; pre-upgrade sessions remain advisory. Tester sessions use safe mode with `todo` only (two turns/70 seconds), recent bounded chat history and no automatic live lab data. `POST /api/sessions/<id>/messages` persists a run, limited atomically to one active run per user. `GET /api/runs` drives two-second UI progress polling; stored steps are sanitized summaries, not raw tool output. Admins see cross-user activity metadata, **not** another user's prompts, replies, chat titles or run steps. Run origin is the portal, not a DAM appliance Gateway; other Hermes channels are not ingested.

A full-admin run can place a browser-captured PNG in a private per-run artifact directory next to SQLite. `GET /api/runs/<id>/screenshot` validates full-mode ownership, file type/size/pixels and serves no-store. The admin-only **Grant website login** form saves an identifier/password under one exact HTTPS origin in the **host-wide Hermes vault**; portal chat does not store that form password. Full-host admins share the vault. It is not a 2FA or shell/cloud approval mechanism. Login/role revocation is rechecked during full runs and kills the CLI process group; already-issued cloud calls or detached children are not rolled back.

## Portal agent versus Hermes gateway

The portal **spawns a new `hermes chat` process for each submitted message** using `subprocess.Popen` with a separate process group, `--query-file -` on stdin and `--format stream-json` on stdout. It is not a gateway plugin and does not inherit this Telegram/gateway conversation. Both surfaces can use the host's Hermes profile and OS/cloud credentials when run under the same account, but their conversations and run controls are separate.

| Aspect | Portal tester | Portal admin | Normal Hermes gateway session |
| --- | --- | --- | --- |
| Context | Last eight portal messages serialized into a fresh advisory prompt; no CLI resume or live lab telemetry | Own portal transcript (up to 12 recent messages); later runs `--resume` the linked Hermes CLI session and repeat safety framing | Gateway-managed conversation/context; portal history is not injected. Actual tools, rules and limits depend on that gateway's configuration. |
| Tools and skills | `--safe-mode --ignore-rules -t todo`; no Imperva skill or AWS/DB query tool | `-t all --skills imperva-troubleshooting`; full host tools, profile and AWS identity | Gateway's configured toolset/skills; not automatically subject to portal tester restrictions. |
| Per-message bounds | `--max-turns 2 --run-budget 70` plus parent timeout | `--max-turns 40 --run-budget 420` plus parent timeout | Gateway configuration, not the portal's per-run budgets. These caps limit iterations/time, **not tokens**. |
| Portal-only checks | Authenticated account and owned session; one active run per user; summaries polled every two seconds | Same, plus current admin/login rechecked while running; process group terminated on failure/revocation | Gateway has its own authorization and approval path; it is not governed by portal roles, request tickets or run-artifact ownership. |

Portal progress stores at most 100 bounded, sanitized event summaries per run; only a small command allowlist is shown verbatim, raw tool output is not exposed. Activity surfaces these timestamped steps and a session link only to the run owner; other admins see attempt/error counts and metadata, not another user's chat/steps. Screenshot retrieval is owner-only. Request approval remains a human handoff: a full admin can operate the host/cloud through another full session without a ticket. The current pilot host has `approvals.single_query_mode=deny`, so a gated headless command is **denied**, not presented as an in-portal approval prompt; a different host must verify its own Hermes settings. The tester toolset and `AWS_EC2_METADATA_DISABLED` environment flag are **not** OS/IAM/network isolation. Both portal workers still run as the server's OS user; an admin's full tools can reach that user's host files, vault and effective AWS permissions. Revocation does not undo completed cloud actions or detached children. These checks make the demo bounded and attributable; they do **not** make it safe for untrusted team-wide access.

## Requests and activity

`POST /api/requests` records a lab-access note; it does not grant access. `POST /api/environments/requests` validates standalone MX/MXHA with 0–4 gateways and required MX version, or a database engine with optional DB/OS versions, plus existing/new attachment and purpose. It writes a pending ticket and proposes a slugged name, not a reserved resource. Admin decisions are recorded at `/api/requests/<id>/decision`; the requester cannot approve their own ticket. For approved typed environment tickets, `/api/requests/<id>/fulfillment` creates or reopens a private **full-host admin planning session** and returns an **unsent** review draft; requester purpose appears for admin review but is omitted from the agent draft. Database handoffs require exact version, compatibility and media selection before a separate authorized build. Approval is a **human handoff**, not enforced authorization: full admins can bypass the ticket through another session. There is no new-environment executor, actual database deployment, expiry/price enforcement or automatic teardown. Invalid legacy tickets require resubmission. `/api/activity` mixes portal runs, requests and EC2 actions; its cross-user rows omit chat text and notes.

**Files and DB advice:** Admin-only `POST /api/files` streams at most 256 MiB of untrusted binary to a 0600 UUID-named file under a private `uploads/` directory beside SQLite; metadata and SHA-256 go into `portal_files`. `GET /api/files` lists metadata, and `GET /api/files/<id>/download` verifies the stored digest and streams an attachment with no-store headers. There is no malware scanner, signature verification, automatic installation or requester access. A full admin Hermes session is told the private directory for an explicitly selected file ID; prompt wording is not an OS sandbox. `POST /api/db-advice` takes only a typed engine and optional versions and invokes a bounded safe-mode Hermes worker to select the next clarification from an enum. The server never returns the worker's free text: it generates unverified guidance from fixed wording, with no live vendor search or version recommendation. Its response is always `needs_verification`; only a separately checked official coverage result and entitled media can support an exact build claim. The worker shares the host OS identity and receives no free-text requester purpose.

**Skill learning review:** `POST /api/sessions/<owned-id>/skill-draft` invokes a separate bounded Hermes CLI with `--safe-mode --ignore-rules -t todo` over the last eight sanitized portal messages; it does not resume the full-privilege admin worker or run live vendor checks, but it still shares the server OS identity (toolset flags are not a sandbox). The generated title, guidance and evidence are validated and stored as an owner-only `draft` in private SQLite. The owner can preview, `POST /api/skill-proposals/<id>/submit`, or `/discard` the draft. Direct user-authored `POST /api/skill-proposals` text is not accepted. `GET /api/skill-proposals` shows a user's own records (including drafts) or the admin queue (submitted proposals only). Neither another admin nor the skill loader sees an unsubmitted draft; raw chat transcript, screenshot and tool output are not copied into a proposal. A **different active admin** posts final edited guidance and a reason to `/api/skill-proposals/<id>/decision`. Rejection changes only the audited record. Approval first records an immutable `approving` intent with the reviewed text in SQLite, then writes only that text to `references/portal-approved-<id>.md` under the installed host `imperva-troubleshooting` directory, adds a pointer to `SKILL.md` and finalizes `approved` in SQLite. If publication is interrupted, the recorded intent can be reconciled on server restart or retried without changing its wording. The write and draft-generation locks are process-local; this is **not** a distributed transaction or multi-server design. A missing/unsafe skill directory leaves the approval intent at `approving` for repair and retry. Redaction heuristics reject obvious secrets but cannot verify model-generated truth, suitability or all confidential text. There is no autonomous promotion, Thales catalog integration or version/patch certification; the owner previews and consents, reviewers verify source material, and an operator confirms a suggested version before separate deployment.

## Persistence and security boundary

SQLite defaults to `~/.local/share/labpilot/portal.sqlite` (0600); screenshot artifacts live in `portal-artifacts/`, and uploaded media in `uploads/`, beside it. Uploaded binary and filenames are private host state, not in Git or a team skills archive. The six exact EC2 pins are read from `~/.config/labpilot-portal/instance-allowlist.private.json` (owner-only 0600); initial bootstrap credentials, when present, are also private and **not** distributed in Git. Git ignores databases, `.env`, keys, credentials and private files. A fresh checkout alone does not reproduce this host's identities or pinned resources.

**Admin = trusted host/cloud operator.** Full Hermes inherits the host profile, private files and broad AWS `AdministratorAccess`. Tester safe mode limits exposed tools, but the worker also inherits the host OS identity; disabling IMDS for that process is not isolation. Exact-ID application checks do not substitute for narrow IAM or separate OS identities. Do not expose this password-only pilot to general teammates or a public endpoint. Independent worker/broker isolation, network/IMDS restrictions, HTTPS/SSO/MFA, audit retention and spend/expiry/cleanup enforcement are prerequisites for a wider deployment. See [DEPLOYMENT.md](DEPLOYMENT.md).
